## 一、问题诊断：当前系统的全景扫描

### 1.1 已发现的技术偏差（来自代码审计）

| 优先级 | 问题 | 位置 | 影响 |
|--------|------|------|------|
| P0 | R04/R05/R06/R08/R_C01~R_C08 规则引擎逻辑不完整 | `admin-api/service/rule_engine.go` | 监管闭环无法真实运行 |
| P0 | R_C05/R_C06/R_C07 是纯 placeholder，无任何逻辑 | 同上 | 社区福利防欺诈检测失效 |
| P0 | `rule_engine.go:312` 变量名冲突 `e` 同时用于循环和 logger | 同上 | 编译错误或逻辑错误 |
| P0 | `crypto.go:80` `base36Encode` 函数签名缺失，混入在 `EncryptAES` 注释块内 | `shared/crypto/crypto.go` | 编译失败 |
| P1 | 规则引擎方法名与调用不一致：`checkNoVerify` 应为 "R01 挂床住院"，但实际逻辑是查 alert 表，未做真正的入院核验检查 | 同上 | R01 误判 |
| P1 | 审计日志 `shared/audit/audit.go` 完全在内存中，服务重启丢失，无持久化 | 同上 | 合规审计不达标 |
| P1 | Gateway 依赖 InfluxDB + Redis，与 CLAUDE.md 规定的 SQLite-only MVP 冲突 | `gateway/cmd/main.go` | 架构不一致 |
| P2 | Push Service 强制依赖 PostgreSQL，与 SQLite 统一存储策略矛盾 | `push-service/cmd/main.go` | 部署复杂度增加 |

### 1.2 业务功能缺口

| 模块 | 缺失功能 | 实际影响 |
|------|---------|---------|
| **规则引擎** | R04(费用突增)、R05(用药与核验不匹配)、R06(频繁转科)、R08(长期不在院) 逻辑不完整 | 监管合规性无法达标 |
| **规则引擎** | R_C01~R_C08 社区规则有框架无实质检测逻辑 | 社区福利欺诈无法发现 |
| **护士终端** | BLE 方案需替换为 NFC A 协议（4cm 近场） | 实际使用无法工作 |
| **API 路径** | 家属APP `hospitalization_page.dart` 调用 `/medical/*` 路径，但 admin-api 的路由在 `/api/v1/admin/medical/*` | 页面数据无法加载 |
| **推送服务** | P0/P1/P2 分级推送策略未落地实现 | SOS 告警可能延迟 |
| **固件** | 手环 Entry/Plus/Pro 无条件编译隔离，Basic 药盒有 WiFi 但 spec 说无 WiFi | 产品定义不一致 |
| **数据隐私** | 无数据脱敏分级策略（老人隐私数据保护不足） | 合规风险 |
| **B2B** | 医院 HIS 预留接口（§9）完全空壳，无实现在线对接能力 | B2B 价值未体现 |

## 二、生态性定位：系统解决什么根本问题

### 2.1 核心问题陈述

**中国老龄化社会的"三个断裂"：**

1. **监护断裂** — 60-85 岁老人独居/空巢，子女在外地工作，老人出现异常时家属无法及时知晓
2. **用药断裂** — 老年人多病共服，遗忘、错服、漏服现象普遍，医院处方与家庭用药信息不互通
3. **监管断裂** — 医院/社区养老资源有限，缺乏低成本、自动化的患者身份核验和福利发放监管手段

### 2.2 系统定位（生态性而非工具性）

Eregen 不是"一个手环+一个APP"，而是一个**银发健康生态平台**：

```
┌──────────────────────────────────────────────────────────────┐
│              Eregen 生态闭环                                   │
│                                                              │
│  [硬件层] 手环/药盒/医用腕带/社区腕带  ← 数据采集入口          │
│       ↓                                                      │
│  [接入层] MQTT + NATS 总线        ← 设备-云端桥梁             │
│       ↓                                                      │
│  [数据层] SQLite(统一) + AI分析    ← 数据沉淀与智能            │
│       ↓                                                      │
│  [规则层] 16条合规规则引擎         ← 自动化监管                │
│       ↓                                                      │
│  [推送层] FCM/短信/微信/SMS 分级   ← 多渠道触达               │
│       ↓                                                      │
│  [应用层] 家属APP/小程序/管理后台/官网  ← 用户交互              │
│       ↓                                                      │
│  [B2B层] 医院/社区/保险  ← 生态扩展                           │
│                                                              │
│  闭环：数据→分析→决策→触达→反馈→再分析                         │
└──────────────────────────────────────────────────────────────┘
```

### 2.3 理论高度：为什么这个系统有价值

**社会价值（非市场性）：**
- 解决子女"远程照护无力感"问题——让关爱可以触达千里之外的父母
- 降低医院"挂床住院"等医保欺诈——每发现一例欺诈，节省数千到数万元医保资金
- 社区福利精准发放——防止重复领取、僵尸账户冒领，让有限资源真正惠及需要的人

**技术价值：**
- 从单一设备到生态平台的完整验证：证明 IoT + AI + 合规引擎 + B2B 的完整技术栈可行
- 专利申请基础：腕带-终端-NFC 核验协议、规则引擎架构、分级推送策略均具备专利性

## 三、完善方案大纲

### 维度一：业务功能完善

#### 3.1.1 规则引擎补全（P0，最高优先级）

**现状：** 16 条规则中 R01-R03、R07 有框架，R04-R06、R08 逻辑不完整，R_C01-R_C08 多为 placeholder。

**完善计划：**

| 规则码 | 名称 | 当前状态 | 需补全内容 |
|--------|------|---------|-----------|
| R01 | 挂床住院 | 框架不完整 | 真正对比入院时间与核验记录，无核验=疑似挂床 |
| R02 | 电子围栏越界 | 框架完整 | 需对接位置数据源（location_records） |
| R03 | 虚假入院 | 逻辑正确 | 补充阈值可配置化 |
| R04 | 费用突增 | placeholder | 实现：当日费用 > 科室日均3倍触发 |
| R05 | 用药与核验不匹配 | placeholder | 实现：有用药记录但无对应核验签名 |
| R06 | 频繁转科 | placeholder | 实现：7天内转科 > 3次触发 |
| R07 | 设备离线 | 框架完整 | 阈值需从配置读取 |
| R08 | 长期不在院 | placeholder | 实现：入院 > 14天未出院且无出院记录 |
| R_C01 | 重复领取 | placeholder | 实现：同老人同月多机构签到 |
| R_C02 | 跨社区互认 | placeholder | 实现：同身份证号跨社区签到 |
| R_C03 | 异常高频 | placeholder | 实现：7天内签到+发药 > 5次 |
| R_C04 | 僵尸账户 | placeholder | 实现：离线 > 30天无签到 |
| R_C05 | 补助未到账 | 空实现 | 实现：福利标签激活 > 7天无支付记录 |
| R_C06 | 跨区领取 | 空实现 | 实现：同福利标签跨区县领取 |
| R_C07 | 福利过期未停 | 空实现 | 实现：福利标签过期后仍激活 |
| R_C08 | 死亡未注销 | 框架不完整 | 实现：死亡状态老人腕带仍在线 |

**技术方案：**
- 每条规则独立为 `EvaluateRXX(ctx) *Alert` 函数，方便测试
- 规则阈值全部从数据库配置表读取，支持动态调整
- 规则执行结果写入 `regulatory_alerts` 表，统一入口
- 增加单元测试覆盖每条规则的边界条件

#### 3.1.2 API 路径对齐（P0，影响3个前端子系统）

**问题：** 家属APP `hospitalization_page.dart` 调用 `/medical/patients/:id/history`，但 admin-api 的路由是 `/api/v1/admin/medical/patients/:id/history`。

**解决方案：**
- 方案A：在 admin-api 中增加无 `/admin` 前缀的 `/api/v1/medical/*` 路由组（推荐）
- 方案B：修改 family-app 和 miniprogram 中的路径前缀为 `/api/v1/admin/medical/*`
- 选择 A：保持 admin-api 作为统一管理入口，family-app 通过统一入口访问医疗数据

#### 3.1.3 护士终端 NFC 方案替换（P0）

**现状：** 使用 BLE 方案，不符合医用腕带 NFC A 协议规范（106kbps，4cm）。

**替换方案：**
- 将 `medical_wristband_ble_service.dart` 替换为 `nfc_wristband_service.dart`
- 使用 Flutter `nfc_manager` 包，支持 ISO 14443-3A（NFC Forum Type 3）
- 协议复用 `shared/protocol/wb_ble.go` 中的数据格式（字节布局一致）
- 验证：PDA 设备（华为/小米支持 NFC）实测读取医用腕带

#### 3.1.4 推送服务优先级路由（P1）

**完善方向：**
- P0（SOS、跌倒）：FCM + SMS 同时推送，确保送达，5秒内响应
- P1（电子围栏、漏服药物）：FCM 为主，短信兜底，15秒内响应
- P2（低电量、设备离线）：FCM 推送，不短信，1分钟内响应
- 增加推送日志表 `push_logs`，记录每次推送的渠道、状态、响应时间

#### 3.1.5 订阅管理补全（P1）

**现状：** 后端有 store 层，但 handler/router 缺少列表端点。

**补全内容：**
- 后端：`GET /api/v1/admin/subscriptions` 分页列表
- 后端：`POST /api/v1/admin/subscriptions/:id/renew` 续费触发
- 前端：管理后台订阅管理页的数据加载和状态流转

#### 3.1.6 B2B 医院对接深化（P2）

**现状：** §9 预留接口完全空壳，无实现在线对接能力。

**完善方向：**
- 实现入院登记同步接口（对接医院 HIS 系统模拟数据）
- 实现出院注销同步接口
- 实现医嘱同步接口（从医院系统拉取用药规则）
- 增加 HL7/FHIR 格式适配层（MVP 用 JSON 模拟）

### 维度二：技术架构完善

#### 3.2.1 数据库统一（P1）

**当前混乱：**
- api-server 使用 SQLite（MVP 策略）
- push-service 强制使用 PostgreSQL
- gateway 同时依赖 InfluxDB + Redis + PostgreSQL/SQLite
- admin-api 支持 SQLite/PostgreSQL 双模式

**统一方案：**
- MVP 阶段：全项目统一 SQLite（与 CLAUDE.md 技术选型一致）
- gateway：移除 InfluxDB 依赖，时序数据写入 SQLite `health_records` 表
- push-service：移除 PostgreSQL 依赖，改用 SQLite
- 保留双存储抽象层（`store` 接口），未来切换 PostgreSQL 只需替换实现

#### 3.2.2 固件三档隔离（P1）

**问题：** Entry/Plus/Pro 功能在代码中无明确边界。

**方案：**
- 在 `firmware/bracelet/` 各 variant 目录下使用条件编译宏：
  ```c
  #ifdef TARGET_ENTRY   // 心率+血氧+SOS+GPS
  #elif TARGET_PLUS     // +电子围栏+跌倒检测
  #elif TARGET_PRO      // +ECG+AMOLED+高精度GPS
  #endif
  ```
- 在 `firmware/pillbox/` 中修复 Basic 版 WiFi 矛盾：删除 Basic 的 WiFi 代码，或更新 spec 为"基础电子版含 WiFi"
- 增加编译脚本 `firmware/scripts/build.sh`，支持 `./build.sh entry` / `./build.sh plus` / `./build.sh pro`

#### 3.2.3 固件 OTA 模块补全（P2）

**现状：** 仅有 stub，Plus/Pro/Smart/Auto 版本缺少 OTA 实现。

**补全内容：**
- 为各 variant 添加 OTA 下载、校验、安装流程
- 增加 OTA 失败回滚机制（双分区 A/B 更新）
- 固件签名验证（Ed25519 签名，与 `shared/crypto` 对齐）

#### 3.2.4 数据管道 AI 分析框架（P2）

**现状：** `data-pipeline` 有健康分析器和风险评分计算器，但 AI 分析引擎框架待完善。

**完善方向：**
- 实现基线计算：根据历史数据计算个人健康基线
- 实现异常检测：超过基线阈值触发告警
- 预留 AI 模型接入点：未来可加载 ML 模型进行预测
- 增加时序降采样：SQLite 存储原始数据，定期降采样存压缩表

#### 3.2.5 统一配置管理（P2）

**现状：** 各服务有独立 config 文件，规则阈值硬编码。

**完善方案：**
- 增加 `cloud/config/` 统一配置中心（YAML/JSON）
- 规则阈值从配置中心读取，支持热更新
- 推送优先级配置集中管理
- 设备超时阈值（如 R07 30分钟）可配置

### 维度三：安全方案完善

#### 3.3.1 设备身份认证强化

**现状：** 使用 Ed25519 签名验证，但缺少设备注册审批流程。

**完善方向：**
- 设备注册流程：ODM 出厂时预置唯一密钥对，注册时需管理后台审批
- 密钥轮换：设备每 90 天重新生成密钥对（OTA 推送新密钥）
- 设备黑名单：发现异常设备可立即吊销访问权限
- 增加设备指纹：记录设备 MAC 地址、IMEI，防止设备克隆

#### 3.3.2 数据传输安全

**现状：** MQTT 使用 TLS，API 使用 JWT，但缺少以下安全措施。

**完善方向：**
- MQTT topic 级访问控制：设备只能订阅/发布自己的 topic
- API 请求签名：敏感操作（用药规则修改、腕带写入）需二次签名
- 传输层加密：家庭宽带环境下使用 DTLS 备用（无 TLS 时降级）
- 数据脱敏：API 返回数据按角色分级（家属看不到详细用药剂量）

#### 3.3.3 数据隐私与合规

**现状：** 基本的数据访问控制，但缺少隐私保护专项设计。

**完善方向：**
- 数据分类分级：健康数据（敏感）、位置数据（极敏感）、设备状态（普通）
- 家属数据权限：仅可查看自己关联的老人数据，不可跨账户访问
- 数据保留策略：健康数据保留 2 年，位置轨迹保留 30 天，告警记录永久
- 用户数据导出/删除：符合 GDPR/个人信息保护法要求
- 医院B2B数据脱敏：保险对接时自动脱敏身份信息

#### 3.3.4 审计日志持久化

**现状：** `shared/audit/audit.go` 审计日志完全在内存中，服务重启丢失。

**完善方案：**
- 审计日志写入 SQLite `audit_logs` 表（与 `init-db.sql` 对齐）
- 日志不可篡改：使用追加写模式，不允许多次修改同一条日志
- 日志分级：INFO（普通操作）、WARN（权限变更）、ERROR（安全事件）
- 日志检索：按时间范围、操作类型、用户 ID 检索

#### 3.3.5 安全管理漏洞修复

**发现的具体问题：**

| 问题 | 位置 | 修复方案 |
|------|------|---------|
| `HashPassword` 函数签名错误（缺少类型声明） | `shared/crypto/crypto.go:72` | 修正函数声明 |
| `base36Encode` 函数嵌套在注释块内 | `shared/crypto/crypto.go:93` | 移出注释块，独立函数 |
| `rule_engine.go:312` 变量 `e` 重复声明 | `admin-api/service/rule_engine.go` | 重命名冲突变量 |
| JWT secret 从环境变量读取但未校验非空 | `admin-api/internal/router/router.go` | 启动时校验，空则报错 |
| API 无速率限制 | 各服务 | 增加 Redis-based 速率限制中间件 |
| SQLite 并发写保护 | 各服务 | 增加 WAL 模式 + 连接池限制 |

### 维度四：生态闭环完善

#### 3.4.1 数据流闭环验证

**现状：** 数据从设备→网关→NATS→存储→应用的通路已建立，但缺少端到端验证。

**完善方向：**
- 增加集成测试：从模拟设备发送心跳→网关接收→NATS发布→数据存储→API查询→前端展示
- 增加告警触发测试：模拟 SOS 事件→规则引擎评估→推送服务分发→家属APP收到通知
- 增加 B2B 数据流测试：医院入院→腕带绑定→护士核验→数据同步到家属APP

#### 3.4.2 家属福利页完善（P1）

**现状：** 福利标签状态页有 UI 原型，但后端 API 和数据处理不完整。

**完善方向：**
- 家属APP/小程序：展示老人福利标签状态（低保/残疾/高龄补贴等）
- 展示补助领取记录和签到提醒
- 与社区腕带签到数据联动

#### 3.4.3 品牌官网内容完善（P2）

**现状：** 官网有基础框架，但缺少产品详情和法律页面。

**完善方向：**
- 三档手环产品详情页（规格对比、购买引导）

#### 3.4.4 小程序功能补全（P2）

**现状：** 小程序有基础框架，但部分页面依赖 mock 数据。

**完善方向：**
- 替换药房/签到 mock 数据为真实 API 调用
- 增加微信小程序订阅消息模板配置
- 优化弱网环境下的数据缓存策略

### 维度五：开发体验与工程规范

#### 3.5.1 测试覆盖提升

**现状：** 部分模块有测试（model_test.go、rule_engine_test.go），但覆盖率低。

**完善方向：**
- 规则引擎：每条规则至少 3 个测试用例（正常触发、边界值、不触发）
- API handler：每个端点至少 1 个成功 + 1 个失败测试
- 固件：增加编译测试（各 variant 独立编译通过）
- 目标：核心模块测试覆盖率 > 60%

#### 3.5.2 代码质量

**发现的问题：**
- `rule_engine.go` 中 R08 检查使用了 `expenses` 变量但未定义（编译错误）
- `rule_engine.go` 中 R_C08 检查方法体混入了 expenses 列表逻辑
- `crypto.go` 函数签名错误

**修复：**

## 五、生态性价值升华

### 5.1 从"设备管理平台"到"银发健康生态"

Eregen 的终极价值不在于"管设备"，而在于：

1. **连接断裂的亲情** — 让千里之外的子女实时知晓父母安危
2. **填补监管空白** — 用技术手段解决医院/社区人力不足的问题
3. **守护生命尊严** — 让老人在熟悉的环境中安全 aging in place

### 5.2 专利布局方向

| 专利方向 | 技术方案 | 预期保护范围 |
|---------|---------|------------|
| 医用腕带-NFC核验协议 | 腕带存储患者信息，护士终端近场秒级读取 | 协议格式 + 核验流程 |
| 分级推送策略 | P0/P1/P2 三级告警 + 多渠道智能分发 | 推送路由算法 |
| 规则引擎架构 | 16条规则统一调度 + 阈值动态配置 | 规则引擎架构 |
| 设备-云端通信协议 | MQTT topic 设计 + JSON 消息格式 | 通信协议 |

### 5.3 未来扩展方向（MVP 之后）

- **AI 健康预测**：基于历史数据预测健康风险（跌倒前兆、用药依从性下降）
- **语音交互**：手环增加语音播报，药盒增加 TTS 提醒
- **智能家居联动**：与小米/华为智能家居联动，老人异常时自动调整家庭环境
- **可穿戴医疗级传感器**：接入 ECG、血压等医疗级数据
- **多语言国际化**：支持 English/Japanese/Korean，拓展海外市场

## 六、总结

本方案从 **业务功能、技术架构、安全方案、生态闭环** 四个维度对 Eregen 系统进行了全方位诊断和完善规划。核心原则是：

1. **先修复，再完善** — P0 编译错误和阻断性问题优先处理
2. **生态性思维** — 每个功能的完善都要问：它如何增强整个生态的闭环？
3. **技术一致性** — 统一到 SQLite、统一的安全标准、统一的 API 设计
4. **专利导向** — 所有核心自研代码都具备专利申请潜力

本大纲为总体方向指引，具体实施时将按阶段拆分为可执行的 issue 列表，每个 issue 独立可测试、可验收。
