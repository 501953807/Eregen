四、数据库架构

⚠ 重要发现：共享单文件SQLite

  • 所有5个服务默认连接 同一个物理文件 data/eregen.db
  • 每个服务有独立的 *sql.DB 连接池，但物理上共享同一数据库
  • 写操作通过SQLite WAL模式 + 行级锁处理并发
  • api-server 和 data-pipeline 都订阅 eregen.event.>，可能导致同一事件被写入两次

八、关键发现与潜在问题

🔴 发现的架构问题

  • 重复写入风险：api-server和data-pipeline都订阅 eregen.event.>，各自的回调都会写入数据库，可能导致同一事件在health_records等表中出现重复
  • NATS Stream重复定义：api-server启动时创建 DEVICE_EVENTS Stream(含eregen.event.>等subjects)，gateway也向同一subjects发布，但gateway不创建Stream——依赖api-server先启动
  • 端口冲突：push-service和data-pipeline默认端口都是8086，生产部署需要区分
  • 双表兼容：health_records(旧)和health_records_v2(新)并存，api-server写入v2但部分查询仍需兼容v1
  • push-service数据库查询依赖api-server写入的表结构：如 user_elderly_links 表可能在api-server的schema中定义，但push-service独立读取

✅ 已验证的正确设计

  • 所有NATS消息使用参数化查询，无SQL注入风险
  • 所有rows正确defer Close，无资源泄漏
  • NULL列使用sql.NullString处理，无NULL→string panic
  • CHECK约束完整(channel枚举值已补全)
  • admin-api和api-server支持SQLite/PostgreSQL双后端
  • 共享模块(8个)全部MIT/BSD许可
  • 52个前端API路径全部匹配后端路由
